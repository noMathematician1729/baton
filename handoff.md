## Why the tested escrow is not V2

The configured address is `0x4f802976810690f984cd05640a23b3ffb5b395e1`. The prepared preflight records that it has code but does not expose `PROTOCOL_VERSION()`; the lifecycle runner requires `keccak256("BATON_JOB_ESCROW_V2")` before any job transaction. The current tracked V2 contract adds:

1. A V2 protocol marker to fail closed against an old ABI/deployment.
2. An expanded EIP-712 `MilestoneOffer` binding the acceptance-spec hash, manifest locator, and sequence. The contract stores the accepted head, sequence, and locator and exposes `acceptedCheckpoint(jobId)` for recovery.
3. Cumulative withdrawals using `withdrawnCredits` instead of a one-time `claimed` flag, plus credited/withdrawn/refunded accounting and `accounting(jobId)`. This allows a worker to claim earlier credit and later claim newly earned milestones.
4. Buyer-only `cancelDrain()` with open-task checks, needed by the confirmed drain-cancellation path.
5. Additional takeover and checkpoint checks, including rejecting a takeover whose successor is already the assigned worker.

Every V2 offer must be signed for the replacement escrow's EIP-712 domain; signatures made for the old escrow cannot be reused. The deployment script also checks the Sepolia chain and ENS resolver/authority-adapter pairing. No replacement has been deployed. The lifecycle runner deploys a fresh test reward token if `BATON_REWARD_TOKEN_ADDRESS` is unset; otherwise the buyer needs at least 10 test tokens.
